### [09-29 19:32] 模型

之前靠的是**运动模型＋逐帧修正**，不需要先训练学习预测器。

以一个向右移动的障碍物为例，系统每帧这样做：

1. **测位置**：把障碍物在画面中的落地点换算成俯视图坐标，并扣除小车自身的移动。
2. **估速度**：用连续几帧的位置，通过卡尔曼滤波估计它现在的位置和速度。
3. **推未来**：先假设它在短时间内大致保持速度。若当前速度是向右 \(0.5\,\text{m/s}\)，那么 1 秒后的预测中心就在右侧约 \(0.5\,\text{m}\) 处，即 \(p_{\text{未来}}=p_{\text{现在}}+v\Delta t\)。
4. **给预测留余量**：障碍物可能加速或转弯，因此用“最大可能加速度”把预测中心扩展成一个随时间变大的**可达范围**，而不是画一个确定点。
5. **处理柱后遮挡**：障碍物消失后，继续推算；将可达范围与柱后看不见的区域相交，得到有依据的蓝色区域。它重新出现后，用新位置修正预测，随后几帧重新估计速度。

避让模块再比较：**在未来同一时刻，小车的候选路线会不会与这个可达范围重叠**。会重叠就评估减速、绕行或停车。

所以此前的预测并非“猜下一帧”，而是基于已测得的速度和物理运动边界做短时推算。它的局限也很明确：**遮挡期间若障碍物突然改变运动，我们无法知道真实变化，只能扩大不确定范围，并在重新看到它后修正。**

把算法做成闭环，关键是让**下一帧观测能纠正上一帧预测，并让纠正后的结果改变下一次决策**。你们需要的运行流程如下：

```mermaid
flowchart LR
    A["相机＋轮速/IMU"] --> B["时间同步与自车定位"]
    B --> C["障碍物检测、地面投影"]
    C --> D["更新世界状态"]
    D --> E["预测未来占用与遮挡风险"]
    E --> F["试算通行、减速、绕行、停车"]
    F --> G["执行动作或显示建议"]
    G --> H["场景继续变化"]
    H --> A
```

### 每一帧具体做什么

| 步骤 | 输入与处理 | 输出 |
|---|---|---|
| 1. 采集 | 读取带时间戳的相机画面、轮速和 IMU；检查数据是否过期 | 同一时刻的传感器数据 |
| 2. 确定自车位置 | 融合轮速与 IMU，估计车在地面坐标系中的位置、朝向、速度 | 自车状态 |
| 3. 发现障碍物 | 单目用地面分割；若改双目则用深度和地面去除。将可靠的障碍物落地点投影到俯视图 | 障碍物位置及检测置信度 |
| 4. **修正世界状态** | 用新检测结果关联已有轨迹，更新卡尔曼滤波；同时更新静态地图和可见区域 | 当前地图、各目标的位置/速度/不确定度 |
| 5. 预测 | 将目标轨迹向未来推演；消失在柱后的目标继续用恒速模型与有界加速度生成可达范围 | 未来多个时刻的可能占用区域 |
| 6. 处理遮挡 | 用柱子的遮挡区与目标可达范围求交，形成**有依据的蓝色区域**；不能因看不见就判为绿色可通行 | 当前未知区和未来风险区 |
| 7. 试算自车动作 | 分别推演保持速度、减速、轻微绕行、停车；按**同一时刻**比较车身与障碍物可能占用区 | 每个动作的碰撞风险与通行代价 |
| 8. 输出决策 | 选安全且能前进的动作；无安全候选或数据过期时停车/提示停车 | 电动小车的控制指令，或手推车的屏幕建议 |
| 9. 下一帧纠错 | 比较“上次预测它现在在哪里”和“现在实际看到它在哪里”，修正位置、速度和不确定度，再执行第 4～8 步 | 形成持续循环 |

这里的**世界模型**不是额外的一张图，而是步骤 4～6 共同维护的状态：`自车状态＋静态地图＋可见性＋障碍物轨迹及不确定度＋未来占用`。学习预测器以后只替换步骤 5，其他步骤无需重写。

### 用柱后场景检查闭环是否真的成立

障碍物在柱前出现时，系统估计速度并预测交叉风险；它进入柱后时，轨迹仍存在，蓝色区域随可能运动范围变化，小车必要时减速；它重新出现时，系统将**预测位置与实际位置对比**，修正速度并重新选择路线。如果画面只播放预先画好的蓝区，或重新出现后决策没有随观测改变，就还没有形成你们想要的闭环。

**手推车与电动小车的区别也要讲准确：**手推车可以完成“实时感知—预测—建议—再次修正”，但实际动作由人执行；电动小车接入电机控制和执行反馈后，才能称为自动避让的物理控制闭环。

### 按什么顺序实现

沿用此前团队计划中“先固定接口、跑通最小链路，再替换加速模块”的方式：

1. **先用录制视频或模拟障碍物位置跑通步骤 3～9**，检查柱前、柱后、重新出现三种状态及决策变化。
2. **接入实时相机和自车定位，在 KV260 上跑通完整软件链**。同时记录每步结果和采集到决策的延迟。
3. **测出瓶颈后做 PL 加速**，优先考虑连续像素处理；加速后仍用同一批场景核对结果，并比较整链延迟。AMD 提供颜色检测等硬件示例，但这些示例仍需与你们的采集和主机程序集成。[AMD Vitis Vision 示例](https://docs.amd.com/r/en-US/Vitis_Libraries/vision/overview.html_5)
4. **最后再考虑学习预测器或电动底盘**，保持前面已经验证的闭环可运行。

开始编码前，建议先约定四类模块数据：`带时间戳的检测结果`、`当前世界状态`、`分时预测占用`、`决策及风险理由`。这样每一步都能单独检查，团队成员也能并行开发。候选动作必须受真实底盘的速度、转向和制动能力约束；这也是 DWA 一类局部规划方法的基本出发点。[DWA 原始论文](https://publications.ri.cmu.edu/the-dynamic-window-approach-to-collision-avoidance)
