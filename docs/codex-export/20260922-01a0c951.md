## 三、实现并行开发的关键：第一周冻结接口

三个人之间真正的依赖不是代码，而是接口。如果接口稳定，即使真实模块没完成，其他人也能用假数据和 Stub 继续工作。

第一周必须完成一份 `接口与数据约定.md`，至少包括：

- 输入、输出的数据形状。
- 每个元素的数据类型和位宽。
- 定点数格式，例如 `ap_fixed<16,6>`。
- 通道排列，例如 NHWC、NCHW或自定义流格式。
- 图像的 RGB/BGR、像素范围和行对齐方式。
- DDR 中的内存布局和缓冲区大小。
- AXI4-Stream 或 AXI4 Memory-Mapped 的选择。
- AXI 数据宽度、`TLAST`、`TKEEP` 的含义。
- 控制寄存器地址、启动方式、中断和错误码。
- 测试输入文件格式。
- “正确”的误差范围。

同时建立三类替身：

- A 给 B：固定输入及期望输出的黄金测试向量。
- B 给 C：假 Kernel 或 Loopback Kernel，输入什么就返回什么。
- C 给 A/B：能够加载文件、启动计算、打印结果的板端框架。

这样 A 不需要等板卡，B 不需要等最终模型，C 不需要等真实 IP。

## 五、每周动态调整机制

每周日晚进行一次 45～60 分钟评审，但不要只是汇报“做了什么”。

每个人必须提交：

- 本周承诺了什么。
- 实际完成了什么。
- 哪个指标发生了变化。
- 当前最严重的一个风险。
- 下周准备交付什么可验证结果。

任务使用四列管理：

| Backlog | 本周进行 | 待验证 | 已完成 |
|---|---|---|---|

“写 Kernel”“优化算法”不能算有效任务，必须写成可以验收的形式，例如：

- “HLS 卷积 Kernel 对 20 组黄金向量误差小于 1%。”
- “板端 640×480 输入下达到 20 FPS。”
- “连续运行两小时无超时、无内存增长。”
- “将 DSP 从 700 降到 500，吞吐下降不超过 5%。”

每周只重排尚未完成的任务，不轻易更换总架构。建议用下面的优先级计算：

`优先级 = 比赛价值 × 风险降低程度 ÷ 预计工时`

某项优化如果需要三天，只能带来 2% 性能提升，却可能破坏已经稳定的系统，就应该推迟或取消。

## 六、KV260 项目必须长期记录的指标

不要只记录 FPS：

- 功能正确率或算法精度。
- 单次时延、平均时延、P95 时延。
- 吞吐率/FPS。
- PS 预处理、数据传输、PL 计算、后处理分别耗时。
- LUT、FF、BRAM、URAM、DSP。
- 目标频率、实际频率、WNS。
- DDR 读写量和有效带宽。
- CPU 占用率。
- 板卡功耗与单次任务能耗，如果条件允许。
- 连续运行稳定时间。

核心关系是：

`系统总时间 = 预处理 + 数据搬运 + PL计算 + 后处理`

不要把 PL Kernel 的周期数当成系统端到端性能。

## 七、推荐的工程结构

```text
project/
├─ algorithm/          # A：Python/C++黄金模型、训练或算法代码
├─ test_vectors/       # 固定输入、期望输出、边界测试
├─ hardware/
│  ├─ hls/             # B：HLS Kernel与testbench
│  ├─ rtl/             # RTL模块
│  └─ platform/        # Vivado/Vitis平台工程与脚本
├─ software/
│  ├─ host/            # C：板端应用
│  ├─ drivers/         # 驱动或XRT封装
│  └─ ui/              # 演示界面
├─ scripts/            # 构建、部署、测试、采集结果
├─ reports/            # 综合、实现、性能、资源报告
├─ docs/
│  ├─ 接口与数据约定.md
│  ├─ 系统架构.md
│  ├─ 实验记录.md
│  └─ 部署与演示手册.md
└─ releases/           # 每周可运行版本
```

每周至少打一个可回退版本，例如 `v0.1-loopback`、`v0.2-first-board-run`、`v0.3-p0-complete`。不要让最终可运行工程只存在于某一个人的电脑上。

最重要的架构原则是：A 定义“什么结果是正确的”，B 负责“怎样在 PL 中高效算出来”，C 负责“怎样让整个系统稳定地用起来”。三条线通过接口文档、黄金向量和替身模块并行推进，而不是靠口头约定互相等待。
