# KV260 自主命题赛道项目执行计划

比赛日期：2026 年 11 月 4 日  
内部完成日期：2026 年 10 月 28 日  
团队人数：3 人

## 一、项目范围原则

自主命题不要一开始追求“大而全”。推荐采用：

> 一个明确应用场景 + 一个可展示的完整系统 + 一个有量化收益的 FPGA 加速核心

选题至少同时满足：

1. 能在 KV260 上现场完整运行；
2. 有 CPU/软件基线可以对比；
3. FPGA 加速部分能够测量延迟、吞吐率和资源占用；
4. 演示效果直观，评委不看源码也能理解价值；
5. 核心 MVP 能在三周内完成。

如果还没定题，9 月 24 日前每人提出一个方案，按以下权重评分：

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 竞赛要求匹配度 | 25% | 是否符合赛道与官方评分方向？ |
| 五周内可实现性 | 25% | 最困难的技术点能否在一周内验证？ |
| 演示效果 | 20% | 能否用画面、波形或数字直观展示？ |
| FPGA 加速价值 | 20% | 是否存在重复计算、并行计算或数据流优化空间？ |
| 数据和外设条件 | 10% | 数据集、摄像头、传感器是否已经具备？ |

不要选择“需要多个未知技术同时成功”的题目。一个项目中最多保留一个高风险创新点。

## 二、三人并行分工

根据成员能力自行映射甲、乙、丙。主责约占个人时间的 70%，交叉验证占20%，文档和答辩占10%。

### 甲：算法、数据与正确性负责人

- 软件参考实现，即 Golden Model；

甲不需要等待硬件完成。第一周就使用纯软件实现，之后用相同输入分别验证 CPU 和 FPGA。

### 乙：FPGA/HLS/RTL 加速负责人

- bitstream/xclbin 等硬件产物；
- 时序、LUT、FF、BRAM/URAM、DSP 报告；
- kernel 级延迟、吞吐率和带宽分析。

乙不需要等待最终算法。第一周使用随机输入和合成测试向量开发；甲后续只需替换黄金数据。

### 丙：KV260 系统、软件与演示负责人

- 摄像头/文件等输入和显示输出；

## 三、并行开发的接口契约

第一周必须冻结 v0.1 接口，至少明确：

- 输入输出的维度、数据类型和数值范围；
- NCHW/NHWC 等数据布局；
- stride、地址对齐和缓冲区大小；
- AXI Memory Mapped 或 AXI Stream；
- 控制寄存器、启动/结束状态和错误码；
- 定点格式以及允许误差；
- 性能统计口径。

建议统一维护四类共享产物：

```text

tests/golden/    固定输入、期望输出、误差阈值
benchmarks/      CPU与FPGA性能、功耗和资源结果
releases/        每周可回退的镜像、程序和硬件产物
```

接口改变必须在每周评审会上决定。禁止在聊天中临时改格式后只通知一个人。

调整优先级固定为：

## 七、必须记录的性能指标

不要只报告 HLS 中的 kernel 延迟。端到端延迟应拆为：

```text
总延迟 =
预处理 +
PS到PL数据搬运 +
硬件计算 +
PL到PS数据搬运 +
后处理
```

物理意义是：FPGA 内部算得再快，如果 DDR 搬运占了大部分时间，用户感受到的系统仍然不会变快。

至少记录：

- CPU 单线程或固定线程数基线；
- kernel 延迟和端到端延迟；
- FPS或每秒处理数量；
- 首帧延迟与稳定吞吐率；
- FPGA 时钟和流水线 II；
- LUT、FF、BRAM/URAM、DSP；
- WNS及是否真正完成时序收敛；
- 空闲与工作功耗、温度；
- 加速前后精度或误差；
- 连续运行成功率。

布局布线后关键资源建议留出约15%—20%的余量。资源“刚好塞满”往往意味着时序、布线和后续修改都会非常困难。
